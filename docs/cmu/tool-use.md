# 工具调用里，Pi Agent 没讲到的那些事｜CMU 11-768 Tool Use

之前拆解过 [Pi Agent 的工具系统](../pi-agent/tool-call.md)。这一篇只补 Pi 没有涉及的部分。

## 一、用代码当工具：CodeAct

普通的工具调用是一问一答：模型输出一个工具调用，harness 执行，结果送回模型，模型再决定下一步。CodeAct 换了一种做法：**让模型直接写一段代码，在代码里调用工具。**

### 一个例子

假设要比较一款手机在美国、日本、德国、印度哪里买最便宜。

- **一步一调**：查德国汇率 → 查德国价格 → 换算加税 → 查日本汇率……四个国家走一遍，要来回十几轮，每个中间结果都要回到模型手里过一遍。
- **CodeAct**：模型写一个 for 循环遍历四个国家，在循环里调用查汇率、查价格的函数，最后比大小。代码执行一次，直接拿到答案。

就像以前事事都要一步一请示，现在直接交一份完整方案，让程序去执行。

### 代码是一种“元工具”

工具并没有被代码取代，而是被代码**组合**了起来。代码提供了普通工具调用没有的三样东西：

1. **控制流**：循环、条件判断。四个国家写一个循环就行，不用调四遍。
2. **变量**：中间结果存在变量里直接往下传，不用回到模型那里再生成一遍。
3. **库**：import 一个 pandas，就等于一次拿到几百个现成的工具。

CodeAct 论文的实验显示，用代码调用工具成功率更高、交互轮数更少，而且这些任务原本并不是写代码的任务。

### 它和 Workflow 有什么不同

两者都是“用代码把工具串起来”，区别在于谁写、什么时候写：Workflow 是开发者事先写死的固定流程；CodeAct 是模型在运行时针对当前任务现写的，跑完看到结果，还能再写下一段。可以理解成：**在 agent loop 的每一轮里，模型现场给自己写一个小 workflow。**

### 代价：代码太强，必须关进沙箱

代码能做的事情没有边界，这既是优点也是风险：

- **可能卡死**：写出死循环，系统得有办法把它停下来。
- **难以约束**：普通工具只能调预先定义好的几个函数，代码却什么都能做，很难提前验证。
- **影响大**：能读写文件、联网、吃光内存和 CPU；还可能引入一个被投毒的第三方库，agent 被攻破，整个系统跟着被攻破。

所以一旦让模型用代码调用工具，就必须配上沙箱、资源限制、权限和审计日志。

### Pi 1.0 的 Codemode：CodeAct 的落地

Pi 1.0 新增的 Codemode 就是这个思路：

- **模型只写脚本**：模型写一段 JavaScript，说清楚调哪些工具、按什么顺序串；脚本在沙箱里自己跑，循环、并发、批量处理都不再经过模型。比如要从一大堆返回数据里筛出 5 条，筛选在脚本里完成，只有精简后的结果回到对话里，省下大量上下文。
- **沙箱很彻底**：脚本运行在编译成 WebAssembly 的 QuickJS 引擎里，没有网络和系统权限，唯一能做的就是调用挂载进来的工具。
- **工具可以只给代码用**：一个工具可以对模型可见、延迟加载（需要时才载入），或者只能从代码里调用，不占模型的工具列表。
- **接入 MCP**：Pi 1.0 正是借助 Codemode 原生支持了 MCP

## 二、约束解码：从源头就不写错

### 先说前提：工具调用其实就是一段文字

模型从头到尾只会做一件事：预测下一个 token。它不会“执行”，只会“写”。所谓调用工具，其实就是模型写出一段特定格式的文字，比如：

```
<tool_call>
{"name": "get_weather", "arguments": {"city": "Pittsburgh"}}
</tool_call>
```

harness 看到 `<tool_call>` 这个记号，就把这段截下来当成指令去执行，再把结果拼回对话里，模型接着往下写。打个比方：模型像一个关在房间里、只能往门外塞纸条的人，门外的助手看到“办事单”格式的纸条，就替他去办。

推理模型的一次回复通常分三段：thinking（很长的内心草稿，不给用户看）、message（给用户看的简短说明）、tool call（给 harness 的办事单）。

每家模型的工具调用格式都不一样：Qwen 用 `<tool_call>` 标签，Mistral 用 `[TOOL_CALLS]` 控制符，DeepSeek 用自己的 DSML 标记语言。这些格式通常是在 mid-training（介于预训练和强化学习之间的训练阶段）学会的。所以微调已有模型时要沿用它原来的格式，解析代码也不能跨模型照搬。

### 问题：写出来的东西就可能写错

既然工具调用是“写”出来的，就可能写错，比如 JSON 少了最后一个 `}`，harness 一解析就报错。与其事后去补括号，不如让模型从源头就写不错。这需要下面几个概念配合。

### Schema：我们写的规定

Schema 是对“数据应该长什么样”的描述，就像一张填表模板。JSON Schema 是最常用的写法：

```json
{
  "type": "object",
  "properties": {
    "city":  {"type": "string"},
    "units": {"enum": ["C", "F"]}
  },
  "required": ["city"]
}
```

意思是：`city` 必填，是字符串；`units` 只能是 C 或 F。Pi 里用 TypeBox 定义工具参数，生成的就是 JSON Schema。

Schema 适合**写完以后整体检查**。但模型是一个 token 一个 token 往外写的，写到一半时，schema 回答不了“下一个字允许是什么”。

### 文法：把规定改写成逐字检查的形式

文法是一套“拼装规则”，规定字符一个接一个该怎么排。把上面的 schema 编译成文法后，其中会有这样一条：

```
unit → "C" | "F"
```

比如 `{"city":"Pgh","units":"K"}`，它是合法的 JSON，但 `unit` 推不出 `"K"`，所以不符合文法。文法的好处是：**写到任何位置，都能说出下一个字允许是什么。**

### 下推自动机：能数清括号的检查机器

文法需要一台机器来执行。最简单的是有限状态自动机（正则表达式就靠它），它只记得“我现在走到哪一步”。但 JSON 可以无限嵌套，收尾时该写 `}` 还是 `]`、写几个，取决于前面开了哪些括号，这台机器记不住。

解决办法是给它加一个**栈**，就像一摞盘子：遇到 `{` 或 `[` 就往上放一个，遇到 `}` 或 `]` 就看最上面那个对不对得上。盘子可以无限高，嵌套多少层都记得住。这台加了栈的机器叫**下推自动机**。

### 约束解码：生成时就不让写错

模型每生成一步，都会给词表里所有 token 打一个分，再按分数挑一个，这叫解码。约束解码就是在挑之前先问一下下推自动机：当前位置哪些 token 合法？不合法的分数直接改成负无穷，只从合法的里面挑。比如写到 "units":" 时，只有 C 和 F 能被选中，模型根本没机会写出 K。这就像手机号输入框，只能打数字：不是等你填完再报错，而是一开始就不让你输错。但要注意，约束解码只保证格式对，不保证内容对：它能保证 city 是字符串，但保证不了填的就是用户想查的那个城市。还有一种情况它也挡不住：模型的输出长度用完了，JSON 写到一半就被截断。

### XGrammar：让检查快到不拖慢生成

原理不难，难的是速度。每生成一个 token，都要对词表里十几万个 token 逐个判断能不能用。更麻烦的是，token 和文法的边界对不齐：比如 `"F"}` 这一个 token 就包含了引号、值、引号、右括号四个部分，只能拆成字节，一个字节一个字节喂给自动机。直接这么算，检查会比生成本身还慢。

XGrammar 是 CMU 团队做的约束解码引擎，主流推理框架都在用。它的提速办法有这几条：

1. **大部分答案提前算好**：在文法的某个位置上，大多数 token 能不能用是固定的。比如写字符串内容时，普通字母永远可以，裸换行符永远不行。XGrammar 在生成之前就为每个位置算好一张表：肯定能用、肯定不能用、说不准。
2. **只现算少数**：“说不准”的 token 要看外面套的是数组还是对象，才需要查栈现场判断，它们只占很少一部分。就像改卷：选择题对着答案卡一扫就完，只有少数开放题要细看。
3. **多个可能共享内存**：文法有歧义时会同时存在几个可能的栈，它们共享相同的部分，不必各复制一份。
4. **CPU 和 GPU 同时干活**：GPU 算下一个 token 的分数时，CPU 已经在算对应的屏蔽表，几乎不用额外等待。

最后说一下分工：写 harness 的人只需要提供 schema，约束解码发生在模型服务商的推理引擎里。Pi 的 `validateToolArguments` 是写完后的事后检查，约束解码是生成过程中的事前拦截，两者互补。

## 三、REST API 与 MCP：钥匙交给谁

这一节回答一个问题：怎么把一个功能开放给 AI 用，开放以后钥匙又交给谁。全程用奶茶店打比方。

### 从一个函数说起

你写了一个 Python 函数 `get_weather(city)`。它就像你会做奶茶的手艺，但只能在自己家里做：只有同一个程序 import 它才能用，别的机器、远处的 AI 都用不了。要让别人用上，就得开一家店。

### 几个基本概念

| 概念 | 是什么 | 奶茶店里 |
| --- | --- | --- |
| API | 一个服务对外说明“能做什么、怎么用” | 整本菜单 |
| 接口 | API 里的某一项功能，比如 `GET /weather` | 菜单上的“珍珠奶茶” |
| 参数 | 调用接口时要填的内容，比如 `city` | 甜度、冰量 |
| 请求 | 某一次具体的调用 | 你递过去的一张小票 |
| 响应 | 服务返回的结果 | 递回来的奶茶 |
| HTTP | 网络上程序之间对话的规则（协议） | 点单和出餐的规矩 |
| JSON | 内容的统一书写格式 | 小票上大家都看得懂的写法 |

一个接口可以收到无数个请求，就像“珍珠奶茶”只有一项，一天却能收到几百张点它的小票。请求和响应其实就是两段文字：

```
请求：GET /weather?city=Pittsburgh&units=F
      X-API-Key: abc123

响应：200 OK
      {"summary": "sunny", "temperature": 72}
```

`200` 是状态码，表示办成了；`401` 表示没带钥匙或钥匙不对；`404` 表示没有这项功能。

### REST API、FastAPI、OpenAPI 分别是什么

- **REST API**：最常见的网络 API 设计风格，每类东西对应一个地址，用 GET（查）、POST（新建）等方法表示动作。相当于大多数店都采用的菜单写法。
- **FastAPI**：一个 Python 库，是“开店工具包”。在函数上加一行 `@app.get("/weather")`，这个函数就挂到了网址上；接收请求、取参数、校验类型、返回 JSON 都由它负责。所以 FastAPI 是工具，REST API 是用它做出来的东西。
- **API key**：一串密码，相当于会员卡，每次请求都放在请求头里。平时说的“申请 API”，就是去办这张会员卡。
- **OpenAPI**：FastAPI 自动生成的说明书，用标准格式列出所有接口和参数。REST API 是“真能点的饮品”，OpenAPI 是“印出来的菜单册”。它的关键在于程序能直接读懂：里面描述参数的部分就是 JSON Schema，harness 下载后稍作改写，就能直接当工具定义交给模型。

### 谁来发请求？钥匙在谁手里？

- **harness 代发**：模型说“我要查天气”，harness 带上 API key 去发请求。钥匙在 harness 手里，模型看不到。安全，但每个服务都要单独接一遍。
- **agent 自己发**：有 shell（终端，用打字的方式指挥电脑，bash 是最常见的一种）的 agent，可以用 curl（命令行里发 HTTP 请求的小工具）自己调用任何接口。很方便，但 API key 就放在 agent 能访问的环境里，它执行一句 `echo $WEATHER_API_KEY` 就能看到。钥匙一旦进了模型的上下文，就可能被写进文件、推到公开仓库，或者被恶意网页骗走。

### MCP：给 AI 用的跑腿中介

MCP（Model Context Protocol）是一套让 AI 应用连接外部工具的标准协议。可以把它想成一个跑腿平台：AI 不直接去店里，而是告诉跑腿要什么，跑腿拿着会员卡去办。它解决两个问题：

1. **统一**：3 个 AI 应用接 4 个服务，原本要写 3 × 4 = 12 套对接代码。有了 MCP，每个服务做一个 MCP server，每个应用学会一套 MCP，3 + 4 = 7 份工作，之后任意组合都能用。
2. **安全**：真正的钥匙不经过 AI。

**三个角色**：Host 是 AI 应用本身，比如 Claude Desktop、Pi 1.0；Server 是真正干活的程序，比如 GitHub MCP；Client 是 Host 里连接某个 Server 的那条线。Server 可以在本地运行（像隔着一根管子传纸条），也可以在远程，通过 HTTP 连接。

**一次完整的调用**，以让 AI 在 GitHub 上建一个 issue 为例：

1. Host 问 Server：你能做什么？（`tools/list`）
2. Server 返回工具清单，每个工具带名字、描述和参数的 JSON Schema。
3. Host 把清单作为工具定义交给模型。
4. 模型输出工具调用：`create_issue`，参数是仓库名和标题。
5. Host 让 Server 去办（`tools/call`），附上 MCP key。
6. Server 检查 MCP key，再用真正的 GitHub token 去请求 GitHub 的 REST API。
7. 结果原路返回给模型。

第 3、4、7 步和普通工具调用完全一样，MCP 只是把“工具从哪来”和“工具怎么执行”标准化了。

**两把钥匙**：

|  | MCP key | 真正的 API key |
| --- | --- | --- |
| 谁拿着 | Host（AI 应用） | MCP server |
| 用在哪一段 | Host → MCP server | MCP server → 真正的服务 |
| 泄露了会怎样 | 影响有限，作废换一把 | 账号被盗 |

所以 API key 并没有消失，只是从 AI 手里转到了中介手里。本地运行、只给自己用的 MCP server 一般不需要 MCP key。除了工具（tools），MCP server 还能提供只读资料（resources）和提示词模板（prompts）。

### FastMCP：开中介的工具包

FastMCP 之于 MCP，就像 FastAPI 之于 REST API。它可以从零写工具（加一个 `@mcp.tool` 装饰器），也可以直接读一份现成的 OpenAPI 说明书，把每个接口自动变成一个 MCP 工具，并替你保管真正的 API key。

### 两点提醒

- MCP 不是必需的。直接调 REST API 完全可以，MCP 的好处是统一和安全。
- 连的 server 一多，工具定义会占掉大量上下文。这正是 Pi 1.0 通过 Codemode 接入 MCP、并支持延迟加载的原因。

**一句话串起来**：用 FastAPI 把函数变成 REST API，并自动生成 OpenAPI 说明书（里面是 JSON Schema）；调用时按 HTTP 发请求、收响应；agent 用 curl 自己调会暴露钥匙，通过 MCP 中介调则碰不到钥匙。

## 四、怎么评测工具调用

模型会不会调用工具，是 agent 能不能完成任务的前提，所以值得单独评测。

### 常用的基准：BFCL

最有名的是 Berkeley Function Calling Leaderboard（BFCL），已经出到第 4 版，一路从简单到复杂：

- **单轮**：一次调用一个或多个工具，包括并行调用。
- **多轮**：缺函数、缺参数、长上下文等情况。
- **Agentic**：网页搜索、记忆等需要多步完成的任务。
- **鲁棒性**：会不会编造参数，换一种工具格式还能不能用对。

### 分四层看

| 层级 | 问的是什么 | 需要真的执行吗 | 典型失败 |
| --- | --- | --- | --- |
| 选工具 | 选对工具了吗 | 不需要 | 漏调或多调 |
| 参数 | 参数值对吗 | 不需要 | 字段或值错了 |
| 顺序 | 调用顺序对吗 | 通常需要 | 有依赖的步骤顺序错了 |
| 任务 | 目标达成了吗 | 需要 | 答案看起来对，其实错了 |

### 除了准确率，还要看三件事

- **效率**：延迟、调用次数、token 数、成本。一个正确但又慢又贵的 agent 也没法用。这里有个反直觉的现象：更贵的模型按单个任务算反而可能更便宜。它更聪明，也更会并行调用工具，一次同时发出多个互不依赖的调用。模型在强化学习中被要求尽快完成任务，于是学会了大量并行。
- **可靠性**：工具超时会不会合理重试，某个工具挂了能不能换别的。
- **安全**：面对诱导它乱用工具的输入，能不能守住。

出错的来源也分三类：模型（选错工具、参数错、忽略结果）、harness（解析失败、认证失败、调用 ID 对不上）、服务商或工具本身（超时、限流、执行出错）。举一个 harness 的例子：如果历史记录里有一个工具调用，却没有对应 ID 的结果（比如程序执行到一半崩了），Anthropic 的接口会判定整段历史无效，直接拒绝继续。

### 同一个模型，换个服务商就不一样

OpenRouter 统计了同一个模型在不同推理服务商那里的工具调用错误率，差距从约 15% 到不足 0.1%。原因主要有四个：

1. **量化程度**：FP8 量化的模型通常比 FP4 出错少得多。FP4 压缩得太狠，省了钱，模型却变差了。
2. **推测解码**：用便宜的小模型先猜、大模型再确认来提速。无损的版本不影响结果，有损的就会。
3. **有没有开约束解码**：第二节讲的那套机制，有的服务商开了，有的没开，没开的就完全靠模型自己写对。
4. **服务本身不稳定**：偶尔宕机，调用自然失败。

所以评测工具调用，除了看基准上的准确率，也要看真实服务环境下的失败率。
