# CMU 11-768 Memory and Skills：Agent 怎么从经验中学习？

之前的上下文管理讲的是怎么让 agent 在一次任务中记住更多有用的信息。这一讲往前走了一步：一次任务结束以后，哪些东西值得留下来，又怎么用在下一次任务中？

这里的学习并不是指重新训练模型，而是通过在模型外部积累经验，让同一个模型越来越会做事。

## 一、做过一次的事情，为什么还要从头做？

假设有两个任务：

- 把 Sony 耳机加入购物网站的收藏夹。
- 查询无线键盘的价格范围。

两个任务的前半部分其实一样：打开网站 → 找到搜索框 → 输入商品名称 → 点击搜索。只有拿到搜索结果之后，才开始做不同的事情。

既然已经知道怎么搜索商品，为什么下一次还要让模型重新探索一遍？

这就像写代码时发现两段重复的逻辑，把它们抽出来封装成一个函数。Agent 的 Skill 也是类似的思想。

### 经验可以存在哪里？

| 存储位置 | 怎么做 | 问题 |
| --- | --- | --- |
| Context Window | 保留之前的对话和操作 | 窗口有限，重复读取成本高 |
| External Artifacts | 存到文件或数据库里 | 需要检索和维护 |
| Model Weights | 通过训练更新模型参数 | 更新成本高，难以迁移 |

这一讲主要讨论第二种。把经验存到模型外面，既方便查看和修改，也有机会在更换底层模型后继续使用。

### Memory 和 Skill 有什么区别？

以做数学题为例，可以留下三种东西：

- Episode（经历）：一道题完整的解题过程。
- Fact（事实）：做题过程中发现的某个知识点。
- Skill（技能）：这一类题的通用解题方法。

Memory 强调的是信息从哪里来，即过去的交互；Skill 强调的是信息能用来做什么，即指导未来的行动。

两者有交集，但不是一回事。开发者提前写好的代码审查规范是 skill，却不是 agent 自己的 memory。从多次代码审查中总结出来的方法，则既是 memory，也是 skill。

## 二、Skill 是怎么写出来、又怎么加载的？

### 人工编写的 Skill（Authored Skill）

假设每次让 coding agent 审查 Python 代码，都要告诉它使用 Black 格式化、Ruff 检查、给公共 API 添加类型注解、使用 Pytest 测试。

与其每次重复输入，不如把这些要求写成一个 skill。

Agent Skills 标准采用的是一种文件夹结构：

```text
python-review/
├── SKILL.md
├── scripts/
├── references/
└── assets/
```

其中 `SKILL.md` 是必需的，其余都是可选的。

- `SKILL.md`：告诉模型什么时候使用这个技能，以及具体怎么做。
- `scripts/`：已经写好的可执行脚本。
- `references/`：需要时查阅的补充文档。
- `assets/`：模板和其他资源。

### Progressive Disclosure：先看目录，再看正文

如果有 100 个 skill，每个 skill 都有几千 token，难道每次调用模型都要把它们全部塞进 system prompt？

显然没有必要。所以 skill 的加载分成三层：

| 层级 | 内容 | 什么时候加载 |
| --- | --- | --- |
| Level 1 | 名称和描述 | 初始加载技能索引时 |
| Level 2 | SKILL.md 正文 | 判断技能相关时 |
| Level 3 | 脚本、文档等资源 | 执行过程中需要时 |

这就像去图书馆找书：先看书名和简介，确定是哪一本，再翻开正文，最后根据需要查阅附录。

课上以 HermesAgent 为例，实际的执行过程是这样的：

1. System Prompt 中放入 skill 的名称和简短描述。
2. 模型判断当前任务需要 Python Review Skill。
3. 调用 `skill_view("python-review")`，正文作为工具结果进入上下文。
4. 如果需要运行脚本，直接通过 terminal 执行，只把运行结果返回给模型。

所以 skill 的文件虽然可能很大，但并不意味着每次都需要消耗这么多 token。

这里还有一个容易忽略的地方：是否加载 skill，在这个实现中是由模型判断的。因此 description 不仅仅是给人看的简介，也是帮助模型选择技能的依据。

### Skill 越多越好吗？

SkillsBench 在 87 个真实任务上进行了实验。提供经过人工筛选的 skill 后，平均通过率从 33.9% 提高到 50.5%，但仍有 13 个任务的表现下降。

较短、数量较少的 skill 通常带来更大的提升。原因之一是模型可能被不相关的指令干扰，甚至放弃原本更好的做法。

OpenHands 建议不要凭空编写 skill，而是先让 agent 完成一次真实任务，再根据执行过程生成 skill，之后多测试几次。

OpenHands 自己维护代码审查 skill 的过程也是这样：记录每次审查结果，看人类实际采纳了哪些建议，分析反复出现的问题，再修改 `SKILL.md`。

## 三、Memory：不只是记住，还要会修改

### MemGPT：把上下文当作内存

MemGPT 在 2023 年提出了一种类似操作系统内存管理的做法。

可以把 context window 理解为 RAM，把外部记忆理解为硬盘。内存里的东西可以直接使用，但容量有限；硬盘能存更多东西，需要时再读回来。

MemGPT 给模型提供了读写外部记忆的工具。比如用户提到以前去过的游乐园，模型可以主动搜索历史记录，把相关内容重新放入当前上下文。

这里的关键是：模型并不是直接看到了整个数据库，而是通过工具调用访问数据库，拿到结果以后才能使用。

### Mem0：新旧记忆冲突怎么办？

假设用户之前说自己在 A 公司工作，后来跳槽去了 B 公司。

如果 memory 只是不断 append，数据库里就会同时存在两条相互冲突的记录。

Mem0 的做法是先从新消息中提取事实，再通过 embedding 检索已有的相似记忆，最后让模型判断该怎么处理。

| 操作 | 含义 |
| --- | --- |
| ADD | 之前没有，新增 |
| UPDATE | 发生变化，更新 |
| DELETE | 原来的事实不再成立，删除 |
| NOOP | 已经存在或没有保存价值，不操作 |

这里让我想到上一讲的 DeltaNet：最初的线性注意力只写不擦，而 DeltaNet 可以修改之前存下来的内容。两者的实现层级不同，一个操作向量，一个操作外部文本，但都在解决记忆不能只增不减的问题。

### Reflexion：把失败原因写下来

除了事实，还可以记住做错事情的原因。

Reflexion 的流程很简单：

```text
执行任务 → 评估结果 → 总结失败原因 → 重新尝试
```

就像做错一道题之后，不只是记住正确答案，还要写下来为什么做错了。下一次尝试时，把这段反思一起交给模型。

另一种做法是直接保存完整的任务轨迹（trajectory），包括工具调用、环境反馈等。新任务来了，通过 embedding 找到相似任务，把之前的执行过程作为 few-shot example。

可以理解为 RAG：普通 RAG 检索的是知识，这里检索的是过去怎么做事的经验。

## 四、让 Agent 自己总结 Skill（Skill Induction）

人工写 skill 的前提是已经知道任务应该怎么做。但如果连开发者都不知道最好的执行方法，就需要 agent 自己探索和总结。

Voyager 就是一个很直观的例子。它让 agent 在 Minecraft 中不断探索，把制作物品等操作封装成函数。简单的函数可以被更复杂的函数调用，技能就这样一点点积累起来。

### AWM：把具体操作变成通用步骤

Agent Workflow Memory（AWM）保存的是文本形式的 workflow。

假设 agent 成功完成了一次搜索商品评论的任务：

```python
click("Marketing")
click("All Reviews")
fill(757, "satisfied")
click("Search")
```

这里的 `satisfied` 是这次任务特有的参数，其他步骤在未来还可能用到。

让 LLM 对这段执行轨迹进行归纳，就能把固定的搜索词替换成变量 `{term}`，得到一个通用的搜索评论流程。

整个过程是：

```text
完成任务
    ↓
Judge：判断任务是否成功
    ↓
Induce：提取可复用的步骤
    ↓
Admit：决定是否收入技能库
```

之后遇到类似任务，模型就可以参考这个 workflow，不必重新摸索。

这种方式叫在线学习（online learning）：任务一个接一个到来，memory 在执行过程中不断积累。注意，这里没有修改模型权重。

### ASI：为什么不直接封装成函数？

文本形式的 workflow 有一个问题：即使模型已经知道操作顺序，还是需要一步步生成工具调用。

Agent Skill Induction（ASI）进一步把技能表示成代码：

```python
def search_product(search_box_id, query):
    click(search_box_id)
    fill(search_box_id, query)
    keyboard_press("Enter")
```

以后模型只需要调用：

```python
search_product("595", "MacBook")
```

这和之前 Tool Use 讲到的 CodeAct 有些相似。区别在于，CodeAct 是模型针对当前任务现场写代码，而这里的代码被保存下来，未来的任务还能继续调用。

代码形式还有一个好处：可以测试。

原始任务成功了，不代表从中提取的函数一定正确。因此可以先用新函数重新执行任务，检查结果，测试通过后再存入技能库。SkillWeaver 还会利用 linter 和执行反馈来修复生成的代码。

ASI 在五个 WebArena 网站上的实验：

| | 检查点达成率 | 平均执行步数 |
| --- | --- | --- |
| No Memory | 41.3% | 24.5 |
| Text Skills | 59.5% | 20.6 |
| Code Skills | 80.2% | 15.0 |

代码技能减少的是模型参与决策的次数。底层的点击、输入操作还是要执行，只是不需要每一步都回来问模型了。

### 代价：代码没有文字灵活

文本告诉模型怎么做，代码直接替模型去做。

比如在一个购物网站上，商品排序通过下拉菜单完成；换到另一个网站，排序却需要打开侧边栏。原来的代码就可能失效，但模型读到文本说明后，还有机会根据当前页面调整操作。

PolySkill 用了一个很熟悉的软件工程思想来解决这个问题：抽象类。

```text
AbstractShoppingSite
├── AmazonShoppingSite
└── TargetShoppingSite
```

先定义统一的搜索、加入购物车、结账接口，再针对不同网站编写具体实现。高层的购物流程只需要调用这些接口，不必关心底层页面长什么样。

所以实际使用中，文本和代码并不冲突。需要灵活判断的部分可以写成文本，重复且稳定的操作可以写成脚本。

## 五、Skill 的生命周期：学会了，还要会忘掉

课件第 25 页把 skill 的生命周期分为三个阶段：

```text
Learn：评估 → 归纳 → 验证 → 存储
Use：检索 → 执行 → 获取反馈
Maintain：新增 → 修复 → 淘汰
```

前面主要讲了怎么学习和使用技能，最后来看看怎么管理已经积累起来的技能库。

### 失败的经验值不值得保存？

ReasoningBank 中有一个例子：agent 搜索 Sony 蓝牙耳机，得到了五千多条结果，然后不断翻页，直到耗尽执行步数。

直接保存这段失败轨迹意义不大，因为下一次模型可能照着错误的操作做一遍。但可以从中提取几条策略：缩小搜索范围、使用筛选条件、增加每页显示数量。

所以成功的经验适合总结成操作步骤，失败的经验更适合总结成教训。

当然，这些经验依赖于 Judge 对任务结果的判断。如果把失败判断成成功，就可能将错误操作收入技能库。ReasoningBank 的实验发现，Judge 越准确，整体表现通常越好，但 Judge 不必完美，记忆机制仍然可以带来收益。

### 检索不是越多越好

ReasoningBank 的另一组实验中，不检索经验时成功率是 39%，检索一条时达到 49.7%，继续增加到四条时反而降到了 44.4%。

Memory 存得多，和每次需要读得多，是两回事。检索出来的经验如果不够相关，只会增加上下文噪声。

### Memory Consolidation：给技能库做减法

TroVE 采用了类似缓存淘汰的思路：根据函数的历史使用频率，删除低频使用的函数。

除此之外，过时的 skill 可以修复，相似的 skill 可以合并。这和维护一个不断增长的代码库很像，不能只添加新功能，从来不做重构。

### 怎么判断一个 Skill 值不值得学？

一个任务成功，只能说明这一次做对了，并不能说明提取出来的 skill 在未来有用。

SAGE 和 AgeMem 尝试用强化学习解决跨任务的经验积累问题。其中 SAGE 不仅奖励任务成功，还奖励后续任务成功复用之前学到的技能。

也就是说，不仅要学会把眼前的事情做完，还要学会为以后的任务留下有价值的东西。

## 小结

| 机制 | 一句话记住 |
| --- | --- |
| Memory | 把有用的经验留到下一次 |
| Skill | 把重复的操作变成通用方法 |
| Progressive Disclosure | 先看目录，需要时再读正文 |
| Skill Induction | 从做过的事情中总结方法 |
| Consolidation | 该更新的更新，该忘记的忘记 |

学完这一讲，发现很多 agent 的设计思想其实在传统计算机科学里早就存在了：内存分层、函数封装、抽象类、缓存淘汰、自动化测试。

不同的地方在于，以前这些工作主要由开发者完成，现在有一部分可以交给模型自己判断和执行。

上下文管理解决的是怎么让 agent 不忘记当前正在做的事情，而 memory 和 skill 解决的是怎么让 agent 不必每次都从头学起。
